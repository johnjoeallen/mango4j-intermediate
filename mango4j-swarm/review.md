# Code and security review

Reviewed production task processing, persistence, configuration, handlers, payload handling, documented schema, and selected tests. This is a static review; no tests were run and dependencies were not independently assessed.

## Finding

- **Timeout recovery can overwrite a concurrent completion or renewed claim** — `src/main/java/ie/bitstep/mango/spring/swarm/db/JdbcTaskRepository.java:130` selects timed-out task IDs in a subquery, but the outer UPDATE checks only `id`. If a task completes or is reclaimed and claimed again while the recovery update waits for its row lock, PostgreSQL can re-evaluate the outer predicate against the new row and still reset it to queued. The analogous timeout-failure query has the same shape. This can re-execute completed work or overwrite a newer attempt. Lock and recheck task state, owner and timeout atomically before updating, and add a concurrent database integration test for completion and re-claim races.

Timeout reclamation can cause overlapping execution if an old handler continues after its lease expires; callers must make external side effects idempotent and use fencing where the downstream system supports it. No tests were run.
- **Worker executes a task even if it lost the claim before starting** — `src/main/java/ie/bitstep/mango/spring/swarm/executor/MangoSwarmDaemon.java:443` calls `markInProgress()` and then executes unconditionally. `JdbcTaskRepository.markInProgress()` silently returns when its guarded update affects zero rows. If timeout recovery requeues or another worker claims the task before the executor starts, the stale worker still performs its side effects. Return an explicit claim-acquired result and execute only on success; test a reclaimed queued task before executor start.
- **Stale progress reports can overwrite the active attempt's runtime** — `src/main/java/ie/bitstep/mango/spring/swarm/db/JdbcTaskRepository.java:319` upserts runtime by task ID without checking the task's current owner or attempt. A timed-out worker continuing to report progress can replace the new worker's runtime state and refresh its timeout timestamp. Guard updates by current owner and an attempt-specific fencing token, and test stale progress after reclaim.

Reviewed the remaining JDBC task methods and schema selection helper. Those areas were reviewed subsequently. No tests were run.
- **Explicit handler failure details are discarded** — `src/main/java/ie/bitstep/mango/spring/swarm/executor/MangoSwarmDaemon.java:477` detects `TaskExecutionResult.Failed` but passes a constant message to failure handling instead of `failed.message()`. This contradicts the `TaskExecutionResult.failed(String)` contract and makes persisted diagnostics unhelpful. Persist an appropriately sanitized and bounded failure message, and test the handler-returned message through retry and terminal failure.
- **Recurring follow-up insertion is not fenced or idempotent across attempts** — `src/main/java/ie/bitstep/mango/spring/swarm/TaskExecutionContext.java:127` documents that `again()` inserts immediately, independently of the current attempt's outcome. A crash, retry, or timeout after the insert can run the handler again and enqueue another follow-up; a stale worker can also enqueue after losing its claim. Applications using this for recurring work can accumulate duplicate series. Provide an attempt-fenced, idempotent scheduling option or require and document deduplication, and test crash/retry and reclaim interleavings.

Reviewed scheduling API, execution context and result, worker registry, payload reader, and handler registry. Configuration, rate limiter, and documented schema were reviewed subsequently. No tests were run.
- **Swarm schema configuration changes the application's Hibernate default schema** — `src/main/java/ie/bitstep/mango/spring/swarm/config/MangoSwarmAutoConfiguration.java:103` applies the Swarm schema to `hibernate.default_schema` by default when the application has not explicitly set one. This setting affects all Hibernate entities, not just Swarm's JDBC tables, so enabling a separate Swarm schema can redirect unrelated application queries or cause startup/runtime failures. Default this global behavior to opt-in or isolate schema configuration to Swarm, and test an application with entities in a different schema.

Reviewed the auto-configuration, properties, rate limiter, executor and wake signal, UUID generator, documented schema, and selected test references. The module relies on application-level idempotency and database access controls; the linked example application has not been reviewed as part of this module review. No tests were run and dependency vulnerabilities were not independently assessed.


## Re-assessment (2026-10-31)

- **Altered:** the module moved from `ie.bitstep.mango.swarm.*` to `ie.bitstep.mango.spring.swarm.*`; paths cited above are the new ones. This is a breaking change for consumers, including the `AutoConfiguration.imports` registration.
- **Verified in code:** there is no SQL injection. All queries are static `PreparedStatement`/`JdbcTemplate` statements with bound parameters, and the only dynamic part, the schema, is validated against `[A-Za-z_]\w*` (max 63 characters) and applied as a bound argument to `set_config('search_path', ?, true)`, scoped to the transaction. The existing lease and fencing findings are unaffected.
