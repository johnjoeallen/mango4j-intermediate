# Code and security review

Reviewed production encryption, registration, HMAC, rotation, helper and annotation code, the module POM, and selected tests. This is a static review; no tests were run and dependency vulnerabilities were not independently assessed.

## Findings

- **Clearing every encrypted field can retain old ciphertext** — `src/main/java/ie/bitstep/mango/crypto/CryptoShield.java:428` only replaces encrypted data when the JSON object is nonempty. If an existing entity's confidential fields are all set to null and encrypted again, the previous ciphertext remains. A later decrypt can restore the old values, defeating deletion and potentially exposing stale sensitive data. Explicitly replace or clear stored ciphertext when all source fields are null, and test an update followed by reload and decrypt.
- **Asynchronous retry can continue mutating an entity after interruption** — `CryptoShield.java:262` schedules an operation and waits on its future; if the waiting thread is interrupted, the method throws without cancelling or waiting for the scheduled task. The task may later encrypt or decrypt the same entity after the caller has handled the error or reused it. Define cancellation and ownership semantics and ensure the task cannot modify the entity after the operation returns; test interruption before and during execution.
- **Encryption and serialization failure can leave a partially modified entity** — `CryptoShield.java:205` mutates the input before invoking the supplied serialization function, with no rollback if encryption or serialization throws. Cascaded encryption can also fail after earlier entities were modified. A caller retrying or continuing after failure can observe mixed old and new cryptographic state. Document the mutation contract and use an atomic staging or restoration strategy where feasible; test failures at each stage.

No tests were run.
- **Compound uniqueness inputs are ambiguous** — `src/main/java/ie/bitstep/mango/crypto/hmac/ListHmacFieldStrategy.java:415` concatenates group field values without delimiters or length encoding. For example, `("ab", "c")` and `("a", "bc")` yield the same HMAC input, producing false uniqueness conflicts; null and the literal string `"null"` can also collide. Use an unambiguous, versioned encoding with explicit null markers and lengths, and plan migration of existing HMACs.
- **Null source fields retain stale single/double HMAC values** — `hmac/SingleHmacFieldStrategy.java:119` and `hmac/DoubleHmacFieldStrategy.java:160` skip a null source without clearing its persisted HMAC fields. Updating a previously populated value to null can leave it searchable by its old HMAC or occupy a unique index. Clear corresponding derived fields on null according to the chosen null semantics, and test updates from non-null to null.

Additional scope: reviewed the single, double, and list HMAC strategy implementations and key ordering. Rotation was reviewed subsequently. No tests were run.
- **Key-on rotation skips encrypted entity types** — `src/main/java/ie/bitstep/mango/crypto/keyrotation/RekeyScheduler.java:123` continues when the entity has encrypted fields, the inverse of the accompanying log message. If the configured services include another type that creates a task, `keyOnLatestEncryptionKey()` can subsequently mark older keys for deletion while encrypted records of the skipped type still depend on them. Correct the condition and require independent proof that every registered encrypted type has completed before retiring keys. Test a mixed set of entity types and key deletion.
- **Interrupted rotation can retire keys prematurely** — `keyrotation/RekeyScheduler.java:379` returns only from the `forEach` lambda after interruption; `rekey()` then returns a count to its caller, which can proceed to mark keys for deletion despite unfinished batches. Propagate interruption as an unsuccessful job and prohibit key retirement unless all tasks completed and verification succeeds; test interruption during batch delay.
- **Failed records are still passed to batch save** — `keyrotation/RekeyScheduler.java:414` catches per-record decrypt or encrypt failures but then saves the entire original batch at line 421. A failed entity can contain partially modified or decrypted fields. Save only successful records in an appropriate transaction and ensure any failure prevents key retirement until the remaining records are verified.
- **Older HMAC KEY_ON validation excludes the oldest key** — `keyrotation/RekeyScheduler.java:245` uses a sublist ending at `size() - 1`, excluding the final (oldest) element. In a two-key list it checks no older key at all. A misconfigured oldest `KEY_ON` key can bypass validation. Include all entries after the newest and test two and three keys.

Reviewed the scheduler, rekey service contract, configuration, key manager, and progress tracker. The scheduler identifies itself as experimental; these findings should be resolved before relying on its key-retirement behavior. The remaining helpers were reviewed subsequently. No tests were run.
- **Cyclic cascade types cause unbounded registration recursion** — `src/main/java/ie/bitstep/mango/crypto/AnnotatedEntityManager.java:112` recursively registers cascade field types without tracking visited classes. A self-referencing or mutually referencing `@CascadeEncrypt` model can overflow the stack during initialization; runtime traversal also lacks cycle detection. Detect cycles or track visited identities during both registration and processing, and test self and mutual references.
- **Registered confidential-field metadata can be modified by callers** — `AnnotatedEntityManager.java:318` returns the internal mutable lists of fields to encrypt, and similar getters expose confidential and cascade lists. A caller can remove a field from the shared registration, causing later encryption to omit it silently. Return immutable snapshots and test attempted mutation.
- **Rekey strategy subclass check is reversed** — `src/main/java/ie/bitstep/mango/crypto/RekeyCryptoShield.java:35` calls `actualClass.isAssignableFrom(ListHmacFieldStrategy.class)` instead of testing whether the actual strategy is an instance of the base class; the same pattern occurs for double HMAC. Subclasses are not wrapped with the rekey-specific strategy and can use normal key-selection behavior during rotation. Use `instanceof` and test subclassed strategies.

Reviewed entity registration, rekey shield, and key iteration. HMAC rekey helpers, annotations and selected tests were reviewed subsequently. No tests were run.
- **Duplicate compound group orders silently omit a field** — `src/main/java/ie/bitstep/mango/crypto/hmac/UniqueGroup.java:14` stores members in a `TreeSet` ordered only by their declared order. Two fields with the same order compare equal, so one is dropped before `ListHmacFieldStrategy.validateUniqueGroupSet()` checks ordering. The resulting uniqueness HMAC excludes a configured field. Reject duplicate orders before insertion and test repeated ordering values.
- **List HMAC rekey assumes every entity implements lookup** — `src/main/java/ie/bitstep/mango/crypto/hmac/RekeyListHmacFieldStrategy.java:47` unconditionally casts the entity to `Lookup`. The list strategy permits an entity with only UNIQUE-purpose fields implementing `Unique` without `Lookup`, so rekeying it throws `ClassCastException`. Check the relevant interface and existing unique entries independently; test a unique-only entity.
- **Multiple group annotations on one field are not handled consistently** — `hmac/UniqueGroupSet.java:51` retrieves repeatable annotations, but `hmac/UniqueGroup.java:22` retrieves a single `UniqueGroup` directly from the field. A field with multiple group annotations can return null there and fail registration, despite the declared repeatable API. Pass the specific annotation through to the group and test a field belonging to multiple groups.

Reviewed the HMAC rekey delegates, unique group helpers, tokenizers, annotations, and repository search helpers. No tests were run. The remaining helpers, module POM and selected tests were reviewed subsequently.
