# Code and security review

Reviewed the production implementation, module POM, and selected tests. This is a static review; no tests were run and dependency vulnerabilities were not independently assessed.

## Findings

- **CBC encryption does not authenticate ciphertext** — `src/main/java/ie/bitstep/mango/crypto/core/encryption/impl/PBKDF2EncryptionService.java:115` permits CBC and returns only IV and ciphertext, without an authentication tag. Altered ciphertext can therefore produce modified plaintext or padding errors, and applications exposing decryption outcomes can create a padding oracle. Restrict new encryption to authenticated modes or use a correctly implemented encrypt-then-MAC scheme; plan authenticated migration for existing CBC data. `CipherManager` also supports CBC, and its callers need separate assessment.
- **Ciphertext controls PBKDF2 work factor** — `PBKDF2EncryptionService.java:152` reads iteration count and key size from the ciphertext container and uses them in PBKDF2 before authenticating anything. If an attacker can submit or alter ciphertext, a very large iteration count can consume CPU and cause denial of service. Validate parameters against a bounded, trusted policy before key derivation and test hostile values.
- **Sensitive derivation material is not cleared** — `PBKDF2EncryptionService.java:285` creates a `PBEKeySpec` and derived byte array without clearing either after use. This unnecessarily extends the lifetime of password and key copies in memory. Clear the spec and temporary byte arrays in `finally` where possible, and document that the configuration's immutable passphrase string cannot be wiped.

No tests were run.
- **Current data key is shared across configurations and service instances** — `src/main/java/ie/bitstep/mango/crypto/core/encryption/impl/wrapped/CachedWrappedKeyEncryptionService.java:52` uses one static cache, and `getCurrentWrappedKeyHolder()` at line 208 returns its current holder without checking the supplied key configuration. Encrypting under a second wrapping key can reuse a data key wrapped under the first; different key sizes or algorithms can also fail or use unintended parameters. This breaks key separation and can prevent correct rotation. Partition cached current keys by the complete trusted key identity and configuration, and test multiple service instances, wrapping keys, and rotations.
- **Key byte cleanup is skipped on errors** — `CachedWrappedKeyEncryptionService.java:145` and `:296` wipe the copied data key only after successful cipher operations. Exceptions during initialization or authentication leave the copy unwiped; `newCachedWrappedKeyHolder()` also wipes its generated bytes only on success, and the cache-miss decrypt path does not wipe `decodedKey` after putting it in the vault. Use `finally` around each owned byte array and test failure paths. The non-cached wrapped implementation also keeps plaintext key bytes and encoded strings without explicit cleanup.
- **Wrapped-key CBC also lacks authentication** — `src/main/java/ie/bitstep/mango/crypto/core/encryption/impl/wrapped/WrappedKeyEncryptionService.java:63` and the cached variant accept CBC through `CipherManager` and store ciphertext without a MAC. Tampering is not detected reliably. Prefer authenticated encryption and define a migration path for existing data.

Additional scope: reviewed the wrapped-key services, holder, and in-memory vault. Other core APIs were reviewed subsequently.
- **Insecure algorithms and test delegates can be registered for production use** — `src/main/java/ie/bitstep/mango/crypto/core/enums/Algorithm.java:21` exposes DES and Triple DES, and `EncryptionService.java:57` accepts all supplied delegates without a production policy or duplicate-type check. The shipped identity and Base64 delegates perform no encryption or real HMAC. Accidental registration or configuration can silently store plaintext or use weak cryptography. Enforce a secure production allowlist and reject duplicate delegate types; isolate test delegates from production artifacts where practical.
- **Malformed ciphertext does not consistently produce a formatter exception** — `src/main/java/ie/bitstep/mango/crypto/core/formatters/CiphertextFormatter.java:40` dereferences required JSON members without validating them and catches only Jackson exceptions. Missing `cryptoKeyId`, a null root, or malformed structure can escape as other runtime exceptions. Validate the shape and size before key lookup and consistently report malformed data; test missing, null, and wrong-type fields.

Reviewed the remaining APIs, domain objects, configuration records, formatter, generators, module POM, and selected tests. This is a static assessment; no tests were run and dependency vulnerabilities were not independently assessed. Security properties also depend on caller configuration and external key providers.


## Re-assessment (2026-10-31)

- **Verified in code:** `PBKDF2EncryptionService` allows CBC (`Mode` has `NONE`, `CBC`, `GCM`) with no authentication tag; `decrypt` reads iterations and key size from the ciphertext container before any integrity check; and `PBEKeySpec` and the derived key bytes are not cleared. All three stand.
- **New (high): decryption trusts the algorithm, mode and padding recorded in the ciphertext.** `decrypt` builds the cipher from `data.get(CIPHER_ALG/MODE/PADDING)` in the stored container, not from the key configuration. Whoever can write stored ciphertext can switch a GCM record to CBC/NoPadding, removing authentication on read. Take mode, algorithm, padding and tag length from the trusted `CryptoKey` configuration, and reject a container that disagrees.
- **New (medium): HMAC computation re-runs PBKDF2 for every holder.** `hmac(...)` derives the key inside the per-holder loop with the full iteration count, although the salt, passphrase and iterations are identical for a given key. This is a CPU amplification path for entities with many HMAC fields and a DoS lever if iteration counts are high. Derive once per key and reuse it.
- **New (medium): `InMemoryKeyVault` does not protect keys against a heap dump.** The AES vault key is stored in the same `VaultEntry` as the IV and ciphertext it protects, so the "encryption" is obfuscation against casual inspection only. Its Javadoc ("Encrypts raw keys with a random AES-256 vault key") overstates the protection; document it as such, or hold the vault key outside the process (HSM/KMS). `get` also rethrows a bare `RuntimeException` instead of the module's crypto exception.
- Positive: all randomness (IVs, key material, vault IVs) uses a shared `SecureRandom`; there is no use of `java.util.Random`, MD5 or SHA-1, and HMAC uses HMAC-SHA256.
- **Altered:** mutation 99% (165/167 killed), coverage 99%; thresholds lowered from 100 to 98 mutation / 99 coverage.
